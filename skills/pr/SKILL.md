# 写 PR 正文

读者是没参与开发的评审人。素材只有两样：本分支的 diff，和 `docs/sdlc/<branch>/` 里已确认的 spec / 票。

## 前提

- 在特性分支上，不是 main/master。
- 改动已全部提交：`git status --porcelain` 输出为空。有未提交内容就停下让人先提交，git 写命令不由智能体执行。
- 有 spec 就先读，PR 的故事要和它对得上；没有就只依据 diff。

## 取改动

基点用 merge-base，避免把主干后来合入的提交算进来。主干按仓库实际情况取（main / develop / origin/main 等），拿不准就问用户：

```bash
BASE=$(git merge-base <主干> HEAD)
git log --oneline "$BASE"..HEAD
git diff --stat "$BASE"..HEAD
```

## 写法

- **简洁**：半屏到一屏。改动小就只留「做了什么」，不要凑满模板。
- **描述性**：写用户和系统能感知的行为变化与意图。不贴代码，不提变量名、函数名、文件名、内部实现。
- **按故事组织**，不按文件罗列：评审人要的是「解决了什么、怎么解决的、有什么坑」，不是改了哪些文件。
- **可验证**：给评审人能自己跑的命令或操作路径。
- 用 `GLOSSARY.md` 的术语；没有就用领域语言。
- 只写 diff 和 spec 支撑得住的内容，不编造动机与效果。

## 模板

按需删节，不留空话。

````markdown
# <一句话说明这个分支做了什么>

## 做了什么

- <3–6 条，按行为分组，每条一两句>

## 为什么

<2–4 句：原来的问题、为什么现在改。没有背景就删掉这节>

## 怎么验证

```bash
<评审人可直接执行的命令；不能命令就写手动操作路径>
```

## 影响与风险

- <行为、配置、数据、兼容性的变化；回滚是否容易；没有就写「无破坏性变更」>
````

## 收尾

- 把正文原样贴给用户，问是否需要调整。
- 不执行 git 写命令，提醒用户用这份正文开 PR。
