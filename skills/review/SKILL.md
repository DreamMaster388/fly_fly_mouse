# 评审

读者是要决定「能不能合」的人。报告只回答三件事：需求做完没有、代码能不能读、会不会出 bug。每条发现要落到 `文件:行`，说清「什么情况下会怎样」和「怎么改」。

## 0. 基点

用户给基点（分支、commit、tag）就用它；没给就问，不要猜。

```bash
BRANCH=$(git branch --show-current)
BASE=$(git merge-base <主干> HEAD)   # 或用户给的 commit
git log --oneline "$BASE"..HEAD
git diff --stat "$BASE"..HEAD
```

diff 为空就停下，说明没有可审的改动。主干名（main / develop / origin/main）按仓库实际取，拿不准问用户。

## 1. 先摸清素材

- `docs/sdlc/<BRANCH>/` 的 spec 与 `issues/*.md`：判断需求是否完成的唯一依据。
- 仓库约定：`AGENTS.md`、`CONTRIBUTING.md`、lint / CI 配置。工具已经强制的规矩不再报。
- 没有 spec：报告里写明「无规格，需求轴只做 diff 内自洽性检查」，别自己替需求下定义。

## 2. 派四个子代理

用 `subagent` 工具，**四条在同一条消息里同时发出**，各自全新上下文、互不通气。不要用 workflow，也不要自己先审一遍再让子代理附和。

四个提示词的公共部分（原样带上）：

> 仓库根 `<REPO_ROOT>`，基点 `<BASE>`。用 `git diff "$BASE"...HEAD` 看改动，需要时读整份文件补上下文。只审本分支改动带来的问题，既有问题不报。
> 不写代码、不改文件、不跑 git 写命令。
> 只报能落到 `文件:行` 的问题，最多 15 条，按严重度降序。凑数的、没有位置的、泛泛而谈的（「建议加强测试」「注意健壮性」）一律不要。
> 每条按下面三行写，几条之间空一行：
>
> ```
> [阻塞|重要|建议] path:line
> 现象: <一句话，主谓宾，说清什么情况下会怎样>
> 为什么: <后果，或违反了哪条约定 / 哪句规格，引用原文一句>
> 怎么改: <具体动作，一句话>
> ```
>
> 全部用中文；代码、命令、路径、标识符保持原样。

### A. 代码质量

只判可读性与结构，正确性问题交给 C，不越界。坏味道基线：神秘命名、重复代码、功能依恋、数据泥团、基本类型偏执、重复分支、霰弹式修改、发散式变化、夸夸其谈通用性、过长消息链、中间人、被拒绝的遗赠。

区分**硬违规**（违反仓库明确约定）和**判断题**（个人偏好），判断题标「可讨论」。

### B. 需求完成度

先列出 spec 与票里的需求编号（R1、R2…），逐条给结论：已实现 / 做了一半 / 缺失 / 超出要求。每条都要证据：实现落在哪个 `path:line`，或哪条测试覆盖。再单列「没被要求的多余改动」。判不准的写「待人工确认」，不要猜。

### C. bug

找真会出错的路径，不找风格问题：错误处理与失败返回、边界与空值、并发与状态、资源释放、时间与时区、数字与精度、权限与安全、迁移与回滚、异常路径下的数据一致性。

每条要给「怎么确认」：能跑的命令、能构造的输入，或指出缺哪条测试。定不了是不是 bug 的写「疑似」，并说明还需要什么信息才能确认。

### D. 测试质量

独立审查新增和修改的测试：是否能真正验证业务行为；是否覆盖边界和异常路径；是否存在过度 Mock；是否通过跳过测试、降低断言或修改预期来使测试通过；是否存在测试与实现相互迎合的问题。在条件允许时，独立设计和执行补充测试。

## 3. 汇总写报告

写 `docs/sdlc/<BRANCH>/review.md`（目录不存在就建；已有内容先读，别丢历史结论）。模板里没内容的节直接删掉，不留空壳。

````markdown
# 评审：<一句话说清这个分支做了什么>

对照：spec / 票 / `<BASE>`..HEAD 的 diff（N 个提交，M 个文件）。

## 结论

<通过 / 有条件通过 / 打回>：<一两句理由。通过＝无阻塞项；有条件通过＝阻塞项都小且改法明确；打回＝方向或设计有问题>

## 必须修（阻塞）

- [ ] [bug] <一句话问题> — `path:line`；影响：<会发生什么>；怎么改：<动作>

## 建议修（不阻塞）

- [ ] [质量] <一句话问题> — `path:line`；影响：…；怎么改：…

## 需求完成度

| 需求 | 结论 | 证据 |
| --- | --- | --- |
| R1 <一句描述> | 已实现 / 做了一半 / 缺失 / 超出要求 | `path:line` 或「缺测试」 |

## 已核对，不成立

<子代理报过、复核后不成立或已被工具强制的项，每条一句话，避免下一个人重复查。没有就删掉这节>

## 怎么验证

```bash
<评审人能直接跑的命令：构建、单测、复现脚本>
```

## 未覆盖

<没审到的分支、没读的模块、需要人工拍板的判断题。没有就写「无」>
````

汇总规则：

- **同一问题只写一次**，标在最对口的轴（`[需求]` / `[质量]` / `[bug]`），别处一句话指回那一条，不复述。
- 阻塞项必须能落到一行代码或一条缺失的测试；落不到就降为建议。
- 数量不是成绩。没有发现就写「未发现」，不要为凑数降低标准。
- 子代理的结论要复核：读一遍它引用的那段代码，对不上就删掉或改写。

## 4. 说人话

- 结论先行：一段话能说清就不列表。
- 主语是代码和行为：「上传大文件时内存会翻倍」，不是「存在内存相关风险」。
- 禁词：闭环、赋能、收敛、抓手、链路打通、健壮性不足、建议持续优化。
- 每条不超过三行；超过说明还没想清楚。
- 术语第一次出现用中文解释一句；引用规格贴原文。
- 不写「另有 N 条未列出」——要么写出来，要么不写。
- 不给自己表功：「已修复」「已闭环」只写事实和验证方式。

## 收尾

- 把「结论 + 必须修」原样贴给用户，再问要不要展开某一轴。
- 不执行 git 写命令。提示下一步：人工提交 → `/pr`。
