# 诊断 bug

## 第 1 步：造一条能变红的回路

这是全部难点。没有能在**这个** bug 上变红的命令，就不要读代码猜原因。

构造方式，按优先级：

1. 失败的测试（单元 / 集成 / e2e）
2. curl 或 HTTP 脚本打 dev server
3. CLI 加 fixture 输入，diff 已知正确输出
4. 无头浏览器脚本，断言 DOM / console / network
5. 重放抓到的 trace
6. 一次性最小 harness
7. fuzz / 属性测试（1000 次随机输入）
8. 二分 harness（`git bisect run`）
9. 新旧版本差分
10. 人在环里的脚本（最后手段）

回路要**紧**：秒级跑完、每次结论一致、断言用户的原话症状。非确定性 bug 就把复现率抬到能调（50% 可调，1% 不可调）。

脱敏：命令、输出、抓包里的密钥一律用 `<REDACTED>`；回路用环境变量传凭据。

## 第 2 步：复现并最小化

跑回路看它变红；确认是用户说的那个失败，不是附近的另一个。然后一次砍一个输入/调用/配置，直到每个剩下的元素都承重——去掉任何一个就变绿。

## 第 3 步：列假设

测之前先列 3–5 个**可证伪**的假设，每个写成「如果 X 是原因，改 Y 会让它消失/更严重」。把排序给用户看，他们常有能立刻重排的信息。用户不在就按自己的排序继续。

## 第 4 步：插桩

一次只改一个变量。优先调试器，其次定点日志，禁止「全打日志再 grep」。日志加唯一前缀（如 `[DEBUG-a4f2]`），收尾一次 grep 清掉。性能问题先建立基线测量，再二分。

## 第 5 步：修复与回归

修之前先写回归测试，但只在**正确的 seam** 上写。seam 太浅、复现不了触发链路时就别写，把「架构缺少可锁死的 seam」本身当作发现记下来。

修完重跑第 1 步的原始回路，确认不再复现。

## 第 6 步：收尾

删掉调试日志与一次性原型；把正确的假设写进 commit / PR 说明。
