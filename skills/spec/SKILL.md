# 规格

不做访谈，只归纳已经聊清楚的东西。

## 前提

- 当前在特性分支上，不是 main/master。
- 对话里已有足够信息；没有就先跑 `/grill`。

## 先定 seam

写规格前，先说出准备在哪些 seam 上验证：优先复用已有接口，用尽可能高的位置，seam 越少越好。与用户确认。

## 写给谁

读者没参加访谈，只读这一份就要判断“这事做不做、做了会错在哪”，并据此拆票。所以：

- 讲决策和约束，不讲实现步骤；
- 结论在前，细节在后，读完第一屏就该能判断；
- 不复述访谈过程，不记录流程状态，不替 README 写用法。

## 唯一真相源

同一个事实只写一次。别的小节要用它，写“见《实现决策》的降级契约”，不要换个说法再讲一遍。

“XX 保持不变”只在有人可能改错时才写，多数情况直接删。

## 写什么

路径 `docs/sdlc/<branch>/spec.md`：

```markdown
# Spec: <标题>

## 问题
用户视角：现在哪里疼、疼到什么程度。≤5 行。

## 方案
用户视角：行为上改了什么。≤10 行。不写签名、参数表、重试细节。

## 用户故事
1. 作为<角色>，我想要<能力>，以便<收益>。
3～7 条，只写用户能感知的变化。

## 实现决策
模块、接口、架构取舍、schema、API 契约。只写会被做错或反直觉的约束：默认值与非法值回退、边界、失败路径、必须保留的旧语义、字段含义。不写文件路径和代码片段。

## 测试决策
seam 位置；每个 seam 断言什么；明确不测什么。断言写到意图粒度。

## 不在范围
读者可能误以为“顺手就做了”的项，≤5 条。

## 补充说明
默认值、兼容性、已知限制、术语与 ADR 链接。已知限制只在这里列一次。
```

文档里不写作者、状态、“确认后运行什么”——那是对话和任务系统的事。

## 跨轮次

新规格取代旧规格时，只写本轮差异。开头一行写清取代谁、哪些契约继续有效（给链接），不要把旧契约重抄一遍；旧契约变了就直接写新值。

## 自检

写完逐条过：

- 目标 ≤100 行。超了先删重复，再删没有后果的已知限制，最后删不会有人误解的“不在范围”。
- 每段问一句：“删掉它，读者会做错什么？”答不上来就删。
- 一个事实出现两次 → 删一处，改成引用。
- 用户故事里出现类名、参数名、函数名 → 挪进实现决策。
- 测试决策在复述实现决策的契约（“content 以…开头、role=summary、replace 是…”）→ 改成断言意图或删掉。
- “取舍”里没有“用 A 换 B”的条目 → 那是风险，合并到已知限制。
- 用户故事超过 7 条 → 多半是把实现决策改写成了故事。

## 反例

| 别写 | 改成 |
| --- | --- |
| 用户故事“我想要能注入假 LLM” | 实现决策：摘要器通过构造注入 LLM，测试用假客户端 |
| 方案里写 `temperature=0.3`、不传 `max_tokens` | 实现决策：复用客户端采样配置，只固定温度 |
| 测试决策重抄“开头声明 + role + replace + usage” | 测试决策：成功路径断言开头声明只出现一次 |
| 不在范围列 15 条未来功能（CLI、UI、模型选择） | 留 3～5 条读者真会误解的 |
| 取舍与已知限制各列 7 条风险 | 取舍只写“用 A 换 B”，风险合并成一处 |

## 收尾

写完给用户看一遍，确认后提示 `/tickets`。
